# 教师偏好与项目叙事

记录日期：2026-09-03。用途：为选题确认、项目范围和数据来源说明准备讨论依据。
后续补充：[Amazon官方业务背景与数据依据](../research/amazon-official-business-background.md)。
教师个人偏好来自组员转述，尚未向教师逐项核实；本文件中的项目建议另行标明，
不替代课程要求，也不代表已经选定演示商品、修改功能规约或完成PPT。

## 教师偏好记录

教师喜欢从具体案例出发，讲清一个人或一家企业为什么需要系统，以及系统在实际工作中
怎样发挥作用。汇报应能沿着业务过程推进，让听众看到问题、操作、结果与决策之间的关系。

转述中的参照案例是财报分析项目：项目使用RAG和大模型，教师要求结合比亚迪的真实财报
走完整个流程，说明企业在这个过程中能获得什么。这个案例对当前项目的启示是用真实材料
贯穿演示；其中的技术选型不自动成为当前项目的需求。

| 关注点 | 转述中的偏好 |
|---|---|
| 业务叙事 | 从企业或用户的具体问题讲起，解释为什么需要系统 |
| 过程完整 | 用一个真实案例展示完整工作流程及业务价值 |
| 前端观感 | 风格简洁、内容丰富，有数据大屏的视觉表现力 |
| 页面示例 | 白色背景、顶部大标题、中心走势图、右侧3D分析图、左下动态词云 |
| 技术追问 | 关注底层架构、整体架构、数据库选择，以及数据如何提取、分离和归档 |
| 前端实现细节 | 据转述较少追问，主要看呈现效果与使用体验 |

这些图表位置和形式是偏好示例，不是教师指定的页面布局。前端实现细节被问得少，也不
改变课程要求：各成员仍须能解释自己负责模块的设计与实现。

## 本次选题确认的用途

PPT可以作为讨论和确认的载体。要确认的实质内容包括选题、服务对象、业务问题、项目范围、
数据来源与规模、整体技术架构，以及初版分工。已有讨论可以成为内容素材，需要再按听众
理解问题的顺序组织。

选题确认阶段展示已有的数据与可行性证据，并说明准备实现的业务过程。最终汇报阶段则用
已经实现的页面、模型结果和真实评论走完过程。当前尚未实现的页面只能标为设计稿，尚未
完成的分析结果只能标为待验证，不能用于证明业务效果。

## 当前项目能提供的证据

现有选题是Amazon商品需求洞察与质量问题预警，面向商品运营人员，使用Amazon Reviews 2023
Appliances历史评论。数据由McAuley Lab发布，文件来源、下载信息、字节数和SHA-256保存在
[manifest](../../data/bronze/amazon_reviews_2023/appliances/manifest.json)。

本轮已完成2,128,605条评论、94,327条商品元数据的基础Silver处理；Spark运行在同一物理机
的两个Worker上，不能称为多物理机集群。原始gzip保持只读，来源行号和稳定ID可追踪。
已验证的质量问题包括2,065条空正文、22,656次精确重复额外出现、285,655次重复正文额外
出现，均保留并标记。证据见[清洗报告](../runs/silver-cleaning-2026-09-03.md)。

语言与NLP准入、近似重复、评分文本矛盾等高级检查仍待评估。MongoDB连接器已通过环境
验收，当前Silver落在Parquet；面向查询的Gold、商家业务页面和正式模型结果尚未完成。
历史评论支持回顾性分析，不能表述成实时监控、真实店铺授权或已经取得企业经营成效。

## 建议讨论的业务故事

可以先设定一个商品运营人员，在准备下一轮产品改进时，面对多个商品的大量评论，需要
判断哪些问题应优先核实、消费者明确提出了什么需求，以及问题是否随时间变化。
角色和工作情境属于演示设定，具体商品与评论必须来自真实数据。

建议用“一个公开品牌或店铺的商品组合 → 一个商品群 → 一个具体父商品”逐步下钻，保持
现有项目范围。贯穿讲述的主角可以是制冰机运营人员；制冰机目前仅是历史探索性候选，
正式采用前需检查商品身份、评论覆盖、时间跨度和业务语义，不能预先决定分析结论。

| 业务步骤 | 运营人员要回答的问题 | 系统计划提供的内容 |
|---|---|---|
| 查看商品组合 | 先看哪个商品，依据是什么？ | 评论量、评分分布、时间覆盖和数据充分性 |
| 进入具体商品 | 用户在讨论哪些使用问题？ | 属性级问题及对应评论数量 |
| 比较时间变化 | 这个问题近期是否更常被提及？ | 分子、分母、月度趋势与样本不足提示 |
| 查阅证据 | 汇总是否符合原文，有没有反例？ | 可回看的评论、日期、评分和上下文 |
| 查找明确需求 | 用户明确希望增加或改善什么？ | 需求表达、主题及原文依据 |
| 形成待办 | 下一步值得核实或改进什么？ | 有证据支持的建议及适用限制 |

制冰机的具体问题，例如噪声、清洁或耐用性，均须经过真实评论分析才能进入故事，不能先
写成“已发现问题”。用户评价中的抱怨也不能直接当作经过工程验证的产品故障。
本项目的价值可以表述为帮助运营人员组织评论证据、发现值得核实的问题和需求；销量、
退款率、成本节省等数据当前没有提供，不应给出未经验证的收益数字。

## 架构如何讲清楚

业务过程中的每一步，都应能对应到数据如何流转。建议围绕同一条真实评论讲清存档、
清洗、聚合、检索和展示，而不是只列技术名称。查询路径和离线计算路径需要分开说明。

| 层次或阶段 | 当前设计中的职责 | 汇报时应解释的问题 |
|---|---|---|
| Bronze | 只读原始gzip、来源清单、摘要 | 数据从哪里来，如何确认完整，为什么保留原始文件？ |
| Spark处理 | 登记来源、字段校验、重复标记、关联、聚合 | 哪些计算由两个Worker实际承担，如何保证行数与身份？ |
| Silver Parquet | 保存可追踪的规范化明细与质量标记 | 清洗改了什么，哪些记录无法参加某项分析，怎样查回原文？ |
| Gold与MongoDB | 保存业务查询所需的汇总、分析结果、证据及批次信息 | 从明细提取哪些结果，为什么这样组织文档与索引？ |
| FastAPI | 查询结果、执行筛选、返回状态与依据 | 前端请求如何落到数据查询，结果不足时如何响应？ |
| Vue/ECharts | 展示指标、趋势、问题、需求与原文证据 | 页面每块内容帮助用户回答哪个业务问题？ |

Gold、MongoDB业务集合和页面仍属计划。后续汇报应展示实际字段、处理规则、批次、存储
位置和一次真实查询，避免用架构图替代实现证据。分层服务于可复现计算、追踪与查询性能，
不要求把完整原始评论重复灌入每个存储系统。

## 页面与PPT表达建议

视觉方向可采用白底、留白清楚、少量强调色，顶部展示项目名和当前分析对象。主区域让
月度趋势占据明显位置，侧边呈现问题分布或比较，底部承接需求主题和评论证据。
筛选商品或月份时，相关图表与证据同步变化，让视觉变化直接对应一次业务操作。

动态词云可以作为主题概览，需要解释词语来源、权重和筛选范围，并能返回评论依据。
问题排序仍需数量、比例和证据支撑。3D图只有在能清楚解释数据维度与业务含义时采用；
形式是否合适，待真实结果和页面草图出现后判断。

选题确认PPT可先讨论约6～8页的篇幅：具体工作情境、用户问题与价值、拟演示的流程、
项目范围、数据来源与已完成证据、四层架构、后续安排与初版分工。页数不是课程硬性要求，
需结合教师给出的确认时长调整。最终成果汇报的页数与内容另行安排。

讨论顺序建议先确定“谁在什么场景下需要什么决定”，再选取能支撑这个过程的真实商品
和评论，最后确定图表与页面。当前待决定的是案例对象、最想呈现的业务决策，以及选题
确认的讲述时长；不因展示偏好另加未经讨论的功能或技术栈。
