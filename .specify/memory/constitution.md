# 大数据 Web 综合实践项目 Constitution

## Core Principles

### I. 规约先于编码（NON-NEGOTIABLE）
任何功能进入编码前，MUST 先有明确的需求规约；进入任务拆分前，MUST 有与需求一致的
设计规约。需求规约 MUST 描述用户目标、范围、验收场景和可验证的成功标准；设计规约
MUST 说明四层架构中的职责、数据流、技术选型及取舍。需求或设计发生变化时，MUST
先更新规约，再更新任务和代码。规约是当前实现的单一真相源，以防止 Vibe Coding 中的
意图漂移，并作为原创开发过程的证据。

### II. 四层端到端闭环（NON-NEGOTIABLE）
系统 MUST 覆盖交互层、业务逻辑层、数据管理与挖掘层、大数据底层处理层，并形成
“数据采集/导入 -> 分布式处理 -> 专用存储与挖掘 -> 业务接口 -> Web 可视化”的可运行
链路。每层 MUST 有清晰边界、可说明的输入输出以及至少一个可演示职责。纯增删改查、
静态图表或绕过大数据处理层的实现不得作为核心方案；这是课程对领域大数据 Web 应用
完整性的基本要求。

### III. 数据真实、合规、可复现
选题 MUST 与实际数据类型和内容匹配。数据来源、版本、许可或使用条件、获取方式、原始
规模和筛选规则 MUST 记录在规约中；自行采集时 MUST 遵守 robots 协议、限制频率、对
个人信息脱敏并按课程要求备案。清洗 MUST 通过可重复执行的程序或任务完成，保留原始
数据不变，并输出清洗前后数量、缺失、重复、异常和过滤统计。任何抽样或缩减 MUST 有
可说明的规则，不得只保留有利于展示的结果。

### IV. 挖掘有效且可解释（NON-NEGOTIABLE）
项目 MUST 包含解决真实业务问题的数据分析或挖掘能力，并在所选大数据处理引擎上完成
具有实质计算量的核心步骤。每项挖掘功能 MUST 定义输入、输出、算法或模型、基线、评价
指标和验收阈值；随机过程 MUST 固定种子，依赖及参数 MUST 版本化。调用现成库可以作为
实现手段，但成员 MUST 能解释特征、算法、参数、复杂度、结果局限及关键实现路径；不得
用无法解释的模型输出或仅调用第三方接口替代核心设计。

### V. 验证、追踪与 AI 使用可问责
每个用户故事 MUST 在实现前定义验收测试或可执行检查；数据管道、跨层接口和核心挖掘
逻辑 MUST 有自动化测试，完整数据运行 MUST 有可复查的日志、指标和失败信息。每次提交
MUST 是可说明的工作单元，并能追踪到规约或任务。所有 Vibe Coding 提示词 MUST 以
Markdown 留档；AI 生成内容 MUST 经成员审阅、测试并理解后方可合入。任何成员无法解释
的核心代码不得进入最终交付版本。

## 课程与技术约束

- 项目数据 MUST 属于图数据、时空轨迹数据或文档类非结构化数据中的一种或多种，并使用
  与数据模型匹配的专用存储。图数据优先使用 Neo4j 或 Dgraph，文档数据优先使用
  MongoDB 或 Couchbase，时空轨迹数据优先使用 MobilityDB 或 TrajMesa；偏离这些标准
  选型 MUST 在设计规约中说明理由并获得教师认可。
- 在未获教师特批时，文档类数据 MUST 不少于 10,000 条，时空轨迹数据 MUST 不少于
  100,000 个轨迹点，图数据 MUST 不少于 10,000 个节点及 30,000 条关系边。
- 大数据底层处理层 MUST 真实使用 Hadoop、Spark 或 Flink 中至少一种；HDFS、Hive、
  HBase 等配套组件按设计需要选用。单机模拟与真实分布式集群的差异 MUST 在报告中如实
  说明，不得把普通脚本包装成分布式处理。
- Web 端 MUST 提供与业务问题相对应的交互和可视化，并允许用户查看挖掘结果及其必要的
  数据依据。可视化不得只是预先生成的截图。
- 正式开发前 MUST 完成选题、初版分工和数据来源说明并通过教师确认。最终材料 MUST
  包含源代码及真实 Git 历史、需求与设计规约、全部 Vibe Coding 提示词、项目报告、
  最终分工表、时长不超过 5 分钟的备份演示视频，以及课程要求时的汇报 PPT。

## 开发流程与质量门禁

1. **治理门禁**：先建立或修订 Constitution，确认课程约束、团队原则和变更规则。
2. **选题门禁**：用需求规约记录问题、目标用户、数据来源、规模证据、业务价值、挖掘
   方法候选和可视化目标；教师确认前不得进入完整功能开发。
3. **规约门禁**：按 `specify -> clarify -> plan -> tasks` 的顺序形成需求、澄清、设计和
   可执行任务。每项任务 MUST 能追踪到用户故事和验收标准。
4. **数据门禁**：先用小样本验证数据结构和清洗规则，再在符合规模门槛的数据上执行
   可复现管道；进入挖掘前 MUST 检查规模与数据质量报告。
5. **实现门禁**：行为实现采用“测试/检查先行 -> 失败证据 -> 最小实现 -> 通过 -> 重构”
   的循环。跨层契约或数据模式变更 MUST 同步更新测试、规约和迁移说明。
6. **集成门禁**：四层链路、核心挖掘、异常路径和性能必须在接近演示环境的配置下验证；
   所有完成声明 MUST 附最近一次命令、日志、指标或演示证据。
7. **交付门禁**：提交前执行规约与实现一致性检查，确保报告、分工、提示词、演示视频和
   实际系统一致；已知限制 MUST 明示，不得用文档描述尚未实现的功能。

## Governance

本 Constitution 对本项目的口头约定、临时提示词和局部开发习惯具有最高优先级。所有
需求规约、设计规约、任务、代码审查和交付检查 MUST 验证其合规性；若某项设计违反原则，
MUST 在实施前修订 Constitution，或提供书面例外说明、影响分析、替代措施和教师/团队
批准记录。

修订必须通过版本化的 Markdown 变更完成，并在文件顶部 Sync Impact Report 中记录影响。
版本遵循语义化规则：删除原则或作不兼容重定义时升 MAJOR；新增原则、约束或实质扩展
治理要求时升 MINOR；不改变含义的澄清和文字修正时升 PATCH。每次功能评审、合并前检查
和最终交付审查 MUST 核对规约追踪、测试证据、数据证据和 AI 提示词留档。复杂度、额外
基础设施及标准技术栈偏离 MUST 在设计规约中给出可验证理由。
