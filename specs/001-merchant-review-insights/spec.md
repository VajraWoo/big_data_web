# Feature Specification: Amazon 商品需求洞察与质量问题预警

**Feature Branch**: `001-merchant-review-insights`

**Created**: 2026-09-02

**Status**: Clarified - ready for planning

**Input**: User description: "面向 Amazon 商品运营人员，从大规模家电评论中识别需要优先解决的质量问题和正在增长的用户需求，并通过趋势、影响程度和代表性评论为产品改进提供证据。"

## Clarifications

### Session 2026-09-02

- Q: 第一版中，哪些商品有资格进入正式的问题排名和趋势预警？ → A: 采用分级准入；
  商品、问题和趋势分别设置资格门槛，但所有正式参数必须通过全量数据分布、统计不确定性、
  覆盖率和预警回测校准，禁止无依据指定。50 条商品正文和 10 条问题证据仅为待检验候选值。
- Q: 第一版应当只识别消费者明确说出的需求，还是也从负面抱怨中推断隐含需求？ → A:
  采用两级结果；明确需求作为经过正式验收的核心结果，隐含需求作为实验性洞察，必须单独
  标识、显示置信度和原文证据，不与明确需求混合排名。
- Q: 第一版应当对全部家电评论统一生成精细问题和需求结果，还是只对业务语义一致的商品群
  生成精细 Gold 结果？ → A: 全量数据完成原始保存、可信明细和通用业务聚合；精细属性
  情感、问题排名、需求发现和预警聚焦经过数据画像选出的业务语义一致商品群。
- Q: 商家进入系统后，第一层应当查看自己的品牌或店铺商品组合，还是直接搜索单个商品？
  → A: 采用品牌/店铺商品组合视角，再下钻到商品群和单个商品；系统使用公开历史数据，
  不验证或暗示当前用户真实拥有该品牌或店铺。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 确定优先改进的问题 (Priority: P1)

商品运营人员先选择公开数据中的品牌或店铺，查看其商品组合概况，再从经过数据质量验证
的商品群下钻到一个商品和时间范围，查看具体属性相关的问题排名，了解每个问题的影响
范围、负面程度、近期变化和可信度，并据此决定优先改进什么。

**Why this priority**: 这是系统的核心决策价值；只有将评论转化为可排序、可解释的改进
事项，系统才不只是普通评论检索或统计看板。

**Independent Test**: 选择一个具有足够评论的商品，系统能够独立给出问题优先级列表，
并展示每项排序的组成依据和评论证据，即可验证该故事。

**Acceptance Scenarios**:

1. **Given** 公开数据中存在可识别的品牌或店铺，**When** 运营人员进入其商品组合，
   **Then** 系统展示组合概况，并允许按商品群和单个商品逐级下钻。
2. **Given** 某商品在所选时期存在足量可分析评论，**When** 运营人员打开问题分析，
   **Then** 系统按优先级展示具体问题，并同时给出提及量、负面比例、趋势和可信度依据。
3. **Given** 运营人员查看某个问题，**When** 展开详情，**Then** 系统展示支持与反驳该
   判断的代表性评论，并标明评论时间、评分、验证购买和有用票信息。
4. **Given** 商品的评论不足以形成可靠结论，**When** 运营人员查看分析，**Then** 系统
   明确提示证据不足，不生成伪精确的问题排名。

---

### User Story 2 - 发现正在增长的用户需求 (Priority: P2)

商品运营人员查看消费者明确表达但现有商品未充分满足的需求主题，比较这些需求的规模、
增长速度、关联商品和原始评论证据，以支持功能规划和详情页改进。

**Why this priority**: 它把评论分析从负面问题总结扩展到产品机会发现，是项目区别于普通
情感分析系统的主要创新点。

**Independent Test**: 在包含明确需求表达的评测评论集中，系统能够聚合语义相近的需求，
展示趋势并返回可核验的原文证据，即可独立验证该故事。

**Acceptance Scenarios**:

1. **Given** 评论中存在多种表达方式相近的未满足需求，**When** 运营人员查看需求洞察，
   **Then** 系统将其聚合为可理解的需求主题，而不是只列出孤立关键词。
2. **Given** 某需求近期提及率显著提高，**When** 系统更新分析结果，**Then** 该需求被
   标为增长需求，并展示用于比较的时间窗口与样本量。
3. **Given** 需求主题证据不足或含义不稳定，**When** 运营人员查看详情，**Then** 系统
   显示低置信度并允许回看原始评论，而不将其表述为确定事实。
4. **Given** 某项需求由负面抱怨推断而非消费者明确提出，**When** 运营人员查看需求洞察，
   **Then** 系统将其标为“隐含需求（实验性）”，且不与明确需求混合进入正式排名。

---

### User Story 3 - 监测商品质量变化 (Priority: P3)

商品运营人员按月查看评论量、平均评分、低评分率和主要问题的变化，并在质量指标或具体
问题发生异常变化时收到可解释的预警。

**Why this priority**: 趋势和预警帮助运营人员及时发现问题，但其价值依赖于 P1 中已经
建立的具体问题识别能力，因此排在第三位。

**Independent Test**: 对具有连续历史评论的商品，系统能展示时间序列并在预先定义的
变化条件被满足时产生包含原因和证据的预警，即可独立验证该故事。

**Acceptance Scenarios**:

1. **Given** 某商品具有跨多个时间周期的评论，**When** 运营人员查看趋势，**Then** 系统
   展示评论量、评分、低评分率及主要问题占比随时间的变化。
2. **Given** 某具体问题的提及率或负面率明显偏离历史基线，**When** 系统执行周期分析，
   **Then** 生成预警，并说明基线、当前值、样本量和触发原因。
3. **Given** 某月评论量过少或时间序列中断，**When** 系统计算趋势，**Then** 对该时段
   标记数据不足，不把小样本波动误报为质量变化。

---

### User Story 4 - 审核结论与数据质量 (Priority: P4)

项目成员或运营人员能够查看数据来源、处理数量、缺失与重复统计、模型评价结果和结论
追踪信息，理解系统可以和不可以说明什么。

**Why this priority**: 课程要求数据过程可复现、核心设计可解释；该故事保证业务结论能够
被审查，而不是无法验证的模型输出。

**Independent Test**: 从任一问题、需求或预警结果出发，能够追踪到计算批次、样本范围、
评价指标和代表性原始记录，即可独立验证该故事。

**Acceptance Scenarios**:

1. **Given** 一次数据处理完成，**When** 项目成员查看质量报告，**Then** 能看到原始、
   接受、标记、排除和关联失败的记录数量，且各项数量可以核对。
2. **Given** 运营人员质疑一个结论，**When** 查看结论详情，**Then** 能看到计算时间范围、
   样本量、置信度、代表性评论和已知局限。
3. **Given** 评分与正文表达明显不一致，**When** 数据被分析，**Then** 该记录被标记供
   审核，但不会仅凭不一致自动删除或判定为虚假评论。

### Edge Cases

- 评论只有评分或标题而没有正文时，评分统计保留该记录，文本任务不使用其缺失部分。
- 商品评论量或时间跨度不足时，不生成趋势、优先级或预警的伪精确结论。
- 商品变体共享父商品时，系统既保留变体身份，也避免把同一父商品误作无关商品。
- 评论找不到商品元数据时，系统保留可用评论并报告关联失败，不静默丢弃。
- 文本并非英文、只包含表情、HTML、链接或极短表达时，系统记录处理结果和任务适用性。
- 完全相同或高度相似的评论跨用户、商品或变体出现时，系统标记重复关系并避免重复计入
  文本主题，但保留原始记录供审计。
- 评分极高或极低时，系统视其为正常业务信号；只有非法范围、错误类型或缺失才属于评分
  字段质量问题。
- 讽刺、否定、混合褒贬或评分与文本不一致时，系统显示不确定性，不将模型结果表述为事实。
- 有用票全部为零、验证购买字段缺失或少数评论获得极高票数时，系统不得让单一字段完全
  支配问题优先级。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 登记并保留 Amazon Reviews 2023 Appliances 原始评论和商品元数据
  的来源、版本、下载时间、文件大小与完整性证据。
- **FR-002**: 系统 MUST 生成数据画像，至少报告记录总量、字段类型、缺失率、正文可用率、
  重复率、语言、评分、时间、验证购买、有用票、商品评论量及候选商品群分布。
- **FR-003**: 系统 MUST 保留原始记录，并形成经过类型校验、时间标准化、重复标记、正文
  适用性标记和商品关联的可信评论明细。
- **FR-004**: 系统 MUST 同时保留商品变体标识和父商品标识，并报告评论与商品元数据的
  关联成功率。
- **FR-005**: 运营人员 MUST 能从公开数据中的品牌或店铺商品组合开始，按“商品组合 ->
  商品群 -> 单个商品”逐级浏览，并在各层选择时间范围；仅当相应元数据真实存在时才提供
  该筛选项。
- **FR-006**: 系统 MUST 展示商品的评论量、平均评分、低评分率、正文可用率和时间趋势，
  并按“可展示基础统计、可进入问题排名、可进入趋势预警”实施分级准入；未达到相应级别
  的结果 MUST 显示明确警告且不得越级展示结论。
- **FR-007**: 系统 MUST 从可用正文中识别具体商品属性或问题主题，并将语义相近的表达
  汇总为运营人员可理解的标签；精细属性体系 MUST 针对已选商品群定义，不得用一套含义
  模糊的通用属性强行覆盖全部家电商品。
- **FR-008**: 系统 MUST 判断评论对具体属性表达的倾向及置信度，并允许一条评论包含多个
  属性和不同倾向。
- **FR-009**: 系统 MUST 根据影响范围、负面程度、近期变化、证据质量和样本充分程度生成
  问题优先级，并向用户解释各组成因素；问题进入正式排名前 MUST 达到经校准的独立评论
  证据门槛，且画像完成后可校准权重，但不得隐藏计算口径。
- **FR-010**: 系统 MUST 识别消费者明确表达的未满足需求，将相近表达聚合为正式需求主题，
  并展示主题规模、趋势、关联商品和代表性证据。
- **FR-011**: 系统 MUST 对评分、低评分率或具体问题相对历史基线的显著变化生成质量预警，
  并使用经校准的历史覆盖、当前窗口和最低样本门槛抑制由小样本直接造成的预警。
- **FR-012**: 每个问题、需求和预警结果 MUST 提供可回看的代表性评论，同时避免只展示
  支持结论而隐藏反例。
- **FR-013**: 系统 MUST 标记评分与文本倾向显著不一致、异常重复或集中爆发的记录，但
  MUST NOT 仅凭这些代理信号宣称评论虚假。
- **FR-014**: 运营人员 MUST 能比较多个符合最低数据要求的商品在问题、需求和趋势上的
  差异，并看到比较双方的样本量。
- **FR-015**: 核心文本分析能力 MUST 与至少一个简单基线进行对照，并报告独立评测集上的
  指标、运行成本、主要错误类型和适用边界。
- **FR-016**: 系统 MUST 记录每批数据从原始记录到可信明细再到业务结果的数量变化、规则
  版本和分析批次，使任一展示结论能够追踪到其数据范围。
- **FR-017**: 系统 MUST 支持不少于 10,000 条文档记录，并以完整 Appliances 类别为目标
  完成一次全量可信明细处理和通用业务聚合结果生成。
- **FR-018**: 面向用户的页面 MUST 在结果缺失、处理未完成、样本不足或分析失败时显示
  可理解的状态，不得用空图表或过期结果冒充有效结论。
- **FR-019**: 系统 MUST 为所有控制商品、问题或趋势准入的参数保存候选值、数据依据、
  选择理由、适用范围和版本；任何阈值变更 MUST 重新生成校准报告，不得直接修改后生效。
- **FR-020**: 系统 MAY 从负面抱怨中推断隐含需求，但 MUST 将其标为实验性结果，记录
  推断依据和置信度，并与明确需求分区展示、分别评测且不得混合进入正式需求排名。
- **FR-021**: 系统 MUST 依据评论量、时间覆盖、元数据可识别性、业务语义一致性和代表性
  选择精细分析商品群，记录所有候选群的保留规模与排除理由；不得仅因某个商品群容易产生
  理想结果而选择它。
- **FR-022**: 系统 MUST 将品牌和店铺标识为公开历史数据中的分析维度，不得要求或暗示
  当前用户完成真实店铺所有权验证，也不得提供真实店铺写入、运营或控制能力。

### Key Entities *(include if feature involves data)*

- **Raw Dataset Release**: 一次外部数据发布，包含来源、版本、文件、下载时间和完整性信息。
- **Review**: 用户对商品的评价，包含评分、标题、正文、时间、商品标识、用户标识、验证
  购买、有用票及数据质量标记。
- **Product and Product Variant**: 被评价的父商品及其颜色、尺寸或款式变体，关联商品名称、
  店铺或品牌、类别、描述和属性元数据。
- **Product Portfolio**: 公开数据中由同一可识别品牌或店铺关联的商品集合，用于组合概况
  和逐级下钻，不表示系统用户对该集合拥有实际控制权。
- **Product Aspect**: 可被评论评价或提出需求的具体属性，如噪声、安装、耐用性或尺寸。
- **Product Group**: 共享可解释业务语义和属性体系的一组商品，包含选择依据、覆盖范围、
  数据充分性和排除规则。
- **Issue Signal**: 某商品属性的负面证据集合，包含规模、负面程度、趋势、置信度和优先级。
- **Demand Topic**: 多条评论共同表达的未满足需求，包含规范名称、相似表达、规模、趋势、
  关联商品以及“明确需求”或“隐含需求（实验性）”来源类型。
- **Quality Alert**: 指标或问题相对历史基线发生值得关注变化的事件，包含触发条件、样本量、
  时间窗口和证据。
- **Representative Evidence**: 用于支持或反驳某项结论的评论引用及其上下文。
- **Processing Run**: 一次可追踪的数据画像、清洗、分析或评测执行，记录输入范围、规则
  版本、数量变化、结果与失败信息。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 数据画像能够核对原始数据中 100% 的记录去向，并在完整类别处理中覆盖至少
  2,000,000 条评论；任何无法解析、关联或参与文本分析的记录都有数量和原因。
- **SC-002**: 在至少 500 条分层人工复核的评论或句子上，属性倾向识别达到不低于 0.75
  的 Macro-F1，且报告不同评分、文本长度和主要属性上的误差。
- **SC-003**: 在至少 300 条包含与不包含明确需求表达的人工复核句子上，明确需求识别
  精确率不低于 0.75、召回率不低于 0.60，并能说明误报和漏报类型；隐含需求单独报告
  探索性指标，不得用于补足明确需求的验收成绩。
- **SC-004**: 对所有进入正式展示的问题、需求和预警，100% 提供样本量、时间范围、计算
  依据、置信度及至少 3 条可核验代表性评论；证据不足时不进入正式排名。
- **SC-005**: 在演示数据和演示设备上，95% 的商品筛选、趋势查看、问题详情和需求详情
  操作在 3 秒内显示已有分析结果。
- **SC-006**: 至少 5 名同学或模拟运营用户中，80% 能在 3 分钟内从品牌或店铺商品组合
  下钻到单个商品，找到最需优先处理的问题并说明原因，且无需项目成员口头解释操作步骤。
- **SC-007**: 对预先构造的明显质量恶化案例，系统在不少于 90% 的案例中产生包含正确
  指标和时间窗口的预警；在稳定对照案例中的误报率不高于 10%。
- **SC-008**: 最终演示能够从任一商家结论追踪到数据批次和评论证据，并且项目成员能够
  解释数据处理、优先级、模型评价与已知局限的完整链路。
- **SC-009**: 每个正式准入参数都有至少 3 个候选值的对比报告，报告同时包含保留商品或
  结果数量、统计不确定性以及对应任务的误报或稳定性指标，并能根据预先声明的规则复现
  最终选择；不存在仅以“经验合适”为理由的参数。
- **SC-010**: 完整 Appliances 类别的全部可解析评论均进入可信明细和通用聚合；至少 2 个
  经选择报告确认、属性语义不同且数据充分的商品群完成精细问题与需求分析，每个商品群
  都能说明其入选与未入选候选群的理由。

## Assumptions

- 第一版使用 Amazon Reviews 2023 的 Appliances 完整原始评论及对应商品元数据，分析的
  是截至 2023 年 9 月的历史数据，不宣称提供 Amazon 实时监控。
- 第一版面向商品运营或产品质量人员，提供分析与决策支持，不执行真实店铺操作，也不
  证明数据中的店铺或品牌就是当前使用者所有。
- 第一版用户界面面向中文使用者，但核心文本分析以英文评论为主；其他语言被识别和统计，
  不强制纳入第一版文本模型。
- 精细分析商品群在补充画像后确定；完整类别仍必须参加数据质量处理和基础业务聚合，
  未进入精细分析的商品不得被描述为已完成属性级需求和问题识别。
- 空正文、极端评分、低有用票或未验证购买不是自动删除条件；记录是否参与某项任务由该
  任务的适用规则决定。
- 画像阶段会比较最低商品样本量、最低独立问题证据、趋势覆盖与窗口、问题优先级权重和
  预警阈值的多个候选值。候选初值可包括 20/50/100 条商品正文、10 条问题证据及
  6/9/12 个活跃月份，但最终参数必须依据覆盖率、置信区间或重采样稳定性、人工评测及
  预警回测选择，不得削弱透明度、证据和小样本保护要求。
- 文本模型可以使用评分作为弱监督信号，但必须通过独立人工复核集评价，评分与文本不一致
  的记录不得同时被当作无误标签和最终异常结论。
- “明确需求”指评论者通过希望、需要、建议、条件愿望或等价表达直接提出改变；由抱怨或
  负面属性进一步推导出的改进方向属于“隐含需求（实验性）”。
- 原始数据仅用于课程研究与本项目验证，不在 Web 应用中公开批量再分发。
